# Lab 03 — ALB 503 Service Unavailable

## Overview

This lab demonstrates how to investigate and resolve an **HTTP 503 Service Unavailable** error generated by an AWS Application Load Balancer (ALB).

We deploy an internet-facing ALB with an Amazon EC2 backend running a Python HTTP server on TCP port 8080.

The ALB uses a target group to forward client requests and performs health checks against the `/health` endpoint.

Initially, the target is registered, healthy, and successfully responds to HTTP requests.

We intentionally deregister the only EC2 target from the target group. The EC2 instance and application continue running, but the ALB no longer has a registered backend to receive requests.

The ALB begins returning HTTP 503 Service Unavailable.

We investigate the listener, target group, registered targets, EC2 status, application health, and CloudWatch metrics. After identifying the empty target group, we register the instance again and verify service recovery.

**Troubleshooting workflow:**

Provision → Healthy Baseline → Fault Injection → Investigation → Root Cause Analysis → Remediation → Verification → Cleanup

## 2. Production Incident Scenario

### Incident Description

A company hosts a web application on an EC2 instance behind an Application Load Balancer.

The ALB receives traffic on port 80 and forwards requests to a backend application listening on port 8080.

The application is running normally, and customers can access it successfully.

During a deployment or infrastructure configuration change, the only EC2 instance is accidentally removed from the ALB target group.

The application remains operational, but the load balancer has no registered target available for forwarding requests.

Users begin receiving HTTP 503 Service Unavailable.

### Incident Symptoms

- ALB returns HTTP 503.
- ALB remains active.
- HTTP listener is correctly configured.
- Target group exists.
- Target group contains zero registered targets.
- EC2 instance remains running.
- Backend HTTP service remains active.
- Backend application returns HTTP 200 locally.
- Security groups permit the intended traffic.
- No application crash has occurred.

### Potential Business Impact

- Customer requests fail.
- Application availability decreases.
- Users cannot access the application.
- API requests return errors.
- Monitoring systems report increased HTTP 503 responses.
- Business services depending on the application may become unavailable.

### Incident Objective

Identify why the ALB returns HTTP 503 despite a healthy backend application, restore target registration, and verify successful client requests.

## 4. Understanding ALB HTTP 503

HTTP 503 means the service is temporarily unable to handle the request.

For an Application Load Balancer, HTTP 503 can occur when the target group selected by the listener has no registered targets.

### ALB Error Comparison

| Error | Meaning | Common Cause |
|---|---|---|
| 502 Bad Gateway | Problem processing backend response | Malformed response or connection reset |
| 503 Service Unavailable | No usable backend destination | Empty target group |
| 504 Gateway Timeout | Backend response not received in time | Connection or response timeout |

### Empty vs. Unhealthy Target Group

**Empty target group**

```text
Registered Targets: 0
ALB Response: HTTP 503
```

**Registered but unhealthy targets**

```text
Registered Targets: 1 or more
Target Health: unhealthy
```

An ALB can fail open when all registered targets are unhealthy, forwarding requests to those targets.

Therefore, an unhealthy target group does not always produce HTTP 503.

### Why Deregistration Matters

Deregistering an EC2 instance removes it from the target group's traffic destinations.

It does not:

- Stop the EC2 instance.
- Terminate the EC2 instance.
- Stop the application service.
- Delete the target group.
- Delete the load balancer.

This separation is the main concept demonstrated in the lab.

## 9. Configure IAM for EC2

### Step 1 — Create Trust Policy

Create `ec2-trust-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

### Step 2 — Check Existing IAM Names

```bash
aws iam get-role --role-name "$ROLE_NAME"

aws iam get-instance-profile \
  --instance-profile-name "$PROFILE_NAME"
```

A `NoSuchEntity` result is expected if the names are unused.

### Step 3 — Create Role and Instance Profile

```bash
aws iam create-role \
  --role-name "$ROLE_NAME" \
  --assume-role-policy-document file://ec2-trust-policy.json \
  --tags Key=Project,Value="$PROJECT_TAG"

aws iam attach-role-policy \
  --role-name "$ROLE_NAME" \
  --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore

aws iam create-instance-profile \
  --instance-profile-name "$PROFILE_NAME" \
  --tags Key=Project,Value="$PROJECT_TAG"

aws iam add-role-to-instance-profile \
  --instance-profile-name "$PROFILE_NAME" \
  --role-name "$ROLE_NAME"
```

Allow IAM propagation before launching the instance.

## 14. Reproduce the HTTP 503 Failure

### Step 1 — Confirm Target Registration

```bash
aws elbv2 describe-target-health \
  --target-group-arn "$TG_ARN" \
  --query 'TargetHealthDescriptions[].{ID:Target.Id,Port:Target.Port,State:TargetHealth.State}' \
  --output table \
  --region "$AWS_REGION"
```

Expected: one healthy target.

### Step 2 — Deregister the Only Target

```bash
aws elbv2 deregister-targets \
  --target-group-arn "$TG_ARN" \
  --targets "Id=$INSTANCE_ID,Port=8080" \
  --region "$AWS_REGION"
```

This is the intentional fault injection.

It removes the EC2 instance from the target group's available destinations but does not stop the EC2 instance.

## 16. Root Cause Analysis

### Root Cause

The only EC2 backend was deregistered from the ALB target group.

The target group contained zero registered targets, preventing the ALB from forwarding incoming requests to the application.

### Technical Explanation

The load balancer received an HTTP request from the client.

Its listener forwarded the request to the configured target group.

However, the target group had no registered backend.

The ALB could not select a target and generated HTTP 503 Service Unavailable.

The EC2 instance remained healthy because deregistration does not stop or terminate the instance.

### Root Cause Flow

```text
Internet Client
       |
       v
ALB HTTP Listener
       |
       v
Target Group
       |
       X
Zero Registered Targets
       |
       v
ALB HTTP 503
```

### Five Whys

1. **Why did clients receive HTTP 503?** The ALB had no registered target to forward traffic to.
2. **Why was the target group empty?** The only EC2 instance had been deregistered.
3. **Why was the EC2 instance still healthy?** Target registration is separate from EC2 instance health.
4. **Why didn't the ALB automatically register the instance?** No Auto Scaling registration or other automation was configured for this lab.
5. **How can this be prevented?** Use multiple targets, Auto Scaling where appropriate, target registration monitoring, and controlled deployment procedures.

## 18. Production Best Practices

### ALB 503 Troubleshooting Checklist

1. Verify ALB state.
2. Inspect HTTP/HTTPS listeners.
3. Confirm listener forwarding actions.
4. Identify the selected target group.
5. Check registered target count.
6. Inspect target health states.
7. Verify EC2 instances are running.
8. Check the backend application.
9. Inspect target registration and deregistration activity.
10. Review CloudWatch 503 metrics.
11. Restore the intended targets.
12. Confirm target health.
13. Verify successful HTTP requests.

### Common Causes of ALB 503

| Problem | Investigation |
|---|---|
| Empty target group | Check registered targets |
| All targets unavailable or unused | Inspect target health and AZ configuration |
| Incorrect listener action | Inspect listener forwarding |
| Target registration removed during deployment | Review deployment workflow |
| Target group attached incorrectly | Verify target group and listener relationship |
| Application scaling configuration problem | Check Auto Scaling and target registration |

### Prevention

- Maintain multiple registered healthy targets.
- Use EC2 Auto Scaling where appropriate.
- Monitor target registration and healthy target counts.
- Configure CloudWatch alarms for ALB-generated 503 errors.
- Use controlled rolling deployments.
- Avoid deregistering the last healthy target without a replacement.
- Review infrastructure configuration through pull requests.
- Use Terraform or CloudFormation for ALB configuration.
- Test application availability after deployments.
- Implement safe deregistration delays.

### Security Best Practices

- Restrict backend SG access to the ALB.
- Prefer HTTPS for production applications.
- Use least-privilege IAM policies.
- Review changes to target group registrations.
- Monitor infrastructure changes with CloudTrail.
- Do not expose backend management ports unnecessarily.

## 20. Interview Questions and Answers

### Q1. What causes an ALB-generated HTTP 503?

A common cause is a listener forwarding to a target group that has no registered targets.

### Q2. What caused HTTP 503 in this lab?

The only EC2 target was deregistered from the target group.

### Q3. Does deregistering a target terminate EC2?

No. It removes the resource from the target group without terminating the instance.

### Q4. Can EC2 remain healthy while ALB returns HTTP 503?

Yes. An EC2 instance can be healthy but not registered with the target group.

### Q5. What command checks target registration?

`aws elbv2 describe-target-health`.

### Q6. What is the difference between ALB 502 and 503?

HTTP 502 generally indicates a backend connection or response problem. HTTP 503 can indicate that the ALB has no registered backend available.

### Q7. Does an unhealthy ALB target always cause HTTP 503?

No. ALBs can fail open and forward requests to unhealthy targets when all registered targets are unhealthy.

### Q8. How do you fix an empty target group?

Register appropriate backend targets and verify that they become healthy.

### Q9. What CloudWatch metric tracks ALB-generated 503 errors?

`HTTPCode_ELB_503_Count`.

### Q10. Why is deregistration delay important?

It allows existing requests and connections to finish before a target is fully removed from service.

### Q11. How can you prevent this issue in production?

Maintain multiple targets, monitor target registration, use Auto Scaling where appropriate, and follow controlled deployment procedures.

### Q12. How would you explain this lab in an interview?

I deployed an AWS Application Load Balancer with an EC2 backend and configured a target group with HTTP health checks.

After confirming the application was healthy and returned HTTP 200, I intentionally deregistered the only EC2 target.

The ALB began returning HTTP 503 Service Unavailable while the EC2 instance and Python application continued running.

I investigated the ALB listener, target group, target registration, EC2 health, and CloudWatch metrics.

I identified the empty target group as the root cause, registered the EC2 instance again, and verified that the ALB returned HTTP 200.

## 22. Lessons Learned

This lab demonstrates that an Application Load Balancer can return HTTP 503 even when the underlying EC2 instance and application are healthy.

Initially, the target group contained one healthy EC2 target, and the ALB returned HTTP 200.

After the target was deregistered, the ALB no longer had a registered backend to receive requests.

The EC2 instance continued running, and its local HTTP server still responded correctly.

The failure was caused by target group registration rather than an application crash or networking misconfiguration.

Registering the EC2 target again restored successful ALB routing.

**Key Lesson:** When investigating ALB HTTP 503 errors, verify the target group has registered targets. A running application cannot receive requests through an ALB unless it is correctly registered and available for forwarding.
