# Lab 04 — ALB 504 Gateway Timeout

## Overview

This lab demonstrates how to troubleshoot an **HTTP 504 Gateway Timeout error generated by an AWS Application Load Balancer (ALB)**.

We deploy an internet-facing Application Load Balancer with an Amazon EC2 backend running a Python HTTP server on TCP port 8080.

The ALB forwards incoming HTTP requests from port 80 to the backend target group. The application provides a `/health` endpoint, a normal `/` endpoint, and a `/slow` endpoint.

Initially, all three endpoints respond successfully with HTTP 200.

We intentionally configure the backend `/slow` endpoint to wait 20 seconds before sending its response. At the same time, the ALB's connection idle timeout is configured to 10 seconds.

Because the backend does not send response data before the ALB timeout expires, the ALB returns HTTP 504 Gateway Timeout.

The EC2 instance remains running, the application service is active, and the registered target remains healthy.

We investigate the backend response time, ALB idle timeout, target health, security groups, application logs, and CloudWatch metrics. After identifying the slow application response as the root cause, we remove the delay and verify successful HTTP requests.

**Troubleshooting workflow:**

Provision → Healthy Baseline → Fault Injection → Investigation → Root Cause Analysis → Remediation → Verification → Cleanup

## 2. Production Incident Scenario

### Incident Description

A company hosts a web application behind an AWS Application Load Balancer.

The ALB receives client requests on port 80 and forwards them to an EC2 backend listening on port 8080.

The backend provides multiple application endpoints.

Most requests complete successfully, but one endpoint performs a slow operation before returning its response.

Following an application or infrastructure change, customers begin receiving HTTP 504 Gateway Timeout when accessing the slow endpoint.

The ALB reports the target as healthy, and EC2 status checks show no infrastructure failure.

The cloud engineering team must investigate why the application is healthy but certain requests are timing out.

### Incident Symptoms

- ALB returns HTTP 504 for `/slow`.
- ALB remains active.
- EC2 instance remains running.
- Backend application process remains active.
- Target group reports `healthy`.
- `/health` returns HTTP 200.
- `/` returns HTTP 200.
- `/slow` takes approximately 20 seconds when tested directly.
- ALB idle timeout is configured to 10 seconds.
- `/slow` fails through the ALB after approximately 10 seconds.
- CloudWatch may show an increase in `HTTPCode_ELB_504_Count`.

### Business Impact

- Slow requests fail.
- API users experience timeouts.
- Application reliability decreases.
- Customers may retry failed operations.
- Excessive retries can increase backend load.
- Operations requiring long processing times may not complete through the ALB.

### Incident Objective

Identify why the ALB returns HTTP 504 even though the backend is healthy, determine whether the failure is caused by timeout configuration or application performance, and restore successful requests.

## 4. Understanding ALB HTTP 504

HTTP 504 Gateway Timeout indicates that a gateway or proxy could not complete a request within the applicable timeout.

An AWS Application Load Balancer can generate HTTP 504 when it establishes a connection to a backend but the backend does not respond before the connection idle timeout expires.

### ALB Error Comparison

| Error | Meaning | Common Cause |
|---|---|---|
| 502 Bad Gateway | Invalid backend response or connection failure | Malformed HTTP, connection reset |
| 503 Service Unavailable | ALB cannot serve a request due to unavailable forwarding destinations | Empty target group |
| 504 Gateway Timeout | Request cannot complete within timeout | Slow backend response |

### What Is the ALB Idle Timeout?

The ALB connection idle timeout determines how long an established connection can remain idle without sending or receiving data.

The default ALB connection idle timeout is 60 seconds.

It can be configured through:

`idle_timeout.timeout_seconds`

For this lab, we deliberately reduce the timeout to 10 seconds.

### How the Failure Happens

```text
ALB Idle Timeout = 10 seconds

Backend Response Delay = 20 seconds

Backend sends no response data for 20 seconds.

10-second idle timeout expires.

ALB returns HTTP 504.
```

### Important Concept

A target can remain healthy even when a particular application endpoint is too slow.

For this lab:

```text
GET /health → HTTP 200 immediately
GET /       → HTTP 200 immediately
GET /slow   → Waits 20 seconds
```

The ALB health checks continue succeeding because they use `/health`, not `/slow`.

## 10. Create the Python HTTP Application

Create `backend-user-data.sh`:

```bash
#!/bin/bash
set -eux

mkdir -p /opt/lab04

cat > /opt/lab04/app.py <<'PY'
#!/usr/bin/env python3

from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from pathlib import Path
import time

FAULT_FILE = Path("/opt/lab04/enable-slow")


class Handler(BaseHTTPRequestHandler):

    protocol_version = "HTTP/1.1"

    def do_GET(self):

        if self.path == "/health":
            body = b"OK\n"

        elif self.path == "/slow":

            if FAULT_FILE.exists():
                print(
                    "Simulating 20-second backend delay",
                    flush=True
                )
                time.sleep(20)

            body = b"Slow endpoint completed\n"

        elif self.path == "/":
            body = b"AWS ELB Lab 04 - Application Healthy\n"

        else:
            body = b"Not Found\n"
            self.send_response(404)
            self.send_header("Content-Type", "text/plain")
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
            return

        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()

        try:
            self.wfile.write(body)
        except (BrokenPipeError, ConnectionResetError):
            print(
                "Client connection closed before response",
                flush=True
            )

    def log_message(self, format, *args):
        print(
            "%s - %s" % (
                self.address_string(),
                format % args
            ),
            flush=True
        )


if __name__ == "__main__":
    server = ThreadingHTTPServer(
        ("0.0.0.0", 8080),
        Handler
    )

    print(
        "Lab 04 HTTP server listening on port 8080",
        flush=True
    )

    server.serve_forever()
PY

cat > /etc/systemd/system/lab04-web.service <<'UNIT'
[Unit]
Description=Lab 04 ALB Timeout Backend
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/bin/python3 /opt/lab04/app.py
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
UNIT

systemctl daemon-reload
systemctl enable --now lab04-web.service
```

### Application Endpoints

| Endpoint | Normal Response | During Failure |
|---|---|---|
| `/health` | HTTP 200 immediately | HTTP 200 immediately |
| `/` | HTTP 200 immediately | HTTP 200 immediately |
| `/slow` | HTTP 200 immediately | HTTP 200 after 20s directly, 504 through ALB |

### Fault Control

Enable slow responses:

```bash
sudo touch /opt/lab04/enable-slow
```

Disable slow responses:

```bash
sudo rm -f /opt/lab04/enable-slow
```

The Python application checks for the file during request handling, so restarting the application is not required to enable or disable the fault.

## 16. Root Cause Analysis

### Root Cause

The backend application waited approximately 20 seconds before returning an HTTP response.

The Application Load Balancer was configured with a 10-second connection idle timeout.

Because the backend did not transmit any response data before the timeout expired, the ALB terminated the request and returned HTTP 504 Gateway Timeout.

### Technical Explanation

When a client requests `/slow`, the ALB forwards the request to the EC2 backend.

The application receives the request and begins processing it.

During fault injection, the application intentionally sleeps for 20 seconds.

The ALB's idle timer expires before the application sends its response.

The load balancer cannot complete the request and generates HTTP 504.

### Root Cause Flow

```text
Client Sends Request
        |
        v
ALB Forwards GET /slow
        |
        v
Backend Receives Request
        |
        v
Application Waits 20 Seconds
        |
        v
ALB Idle Timeout Reaches 10 Seconds
        |
        X
No Response Data Received
        |
        v
ALB Generates HTTP 504
```

### Why Did Health Checks Remain Healthy?

The ALB uses `/health` for target health checks.

The `/health` endpoint responds immediately, while only `/slow` is delayed.

As a result, the target continues passing health checks even though client requests to `/slow` fail.

### Five Whys

1. **Why did users receive HTTP 504?** The ALB did not receive a response before its idle timeout expired.
2. **Why was the backend response late?** The application waited 20 seconds.
3. **Why did the request time out around 10 seconds?** The ALB idle timeout was configured to 10 seconds.
4. **Why was the target still healthy?** The `/health` endpoint responded immediately.
5. **How can the incident be prevented?** Optimize slow operations, monitor response times, configure suitable timeouts, and test application endpoints.

## 18. Production Best Practices

### ALB 504 Troubleshooting Checklist

1. Confirm the client received an ALB-generated HTTP 504.
2. Check ALB state.
3. Inspect listener and target group configuration.
4. Verify target registration.
5. Check target health.
6. Confirm EC2 infrastructure health.
7. Test the backend service directly.
8. Measure application response time.
9. Review the ALB connection idle timeout.
10. Inspect backend application logs.
11. Check CPU, memory, and application resource usage.
12. Review relevant CloudWatch metrics.
13. Check network ACLs and security groups if connection failures are suspected.
14. Identify the exact timeout or latency bottleneck.
15. Apply remediation and verify successful requests.

### Common Causes of ALB 504

| Cause | Investigation |
|---|---|
| Slow application processing | Backend request duration |
| Database query delay | Database latency and connection pool |
| Backend connection timeout | Routing, SG, NACL, target availability |
| Slow external API dependency | Dependency response time |
| Backend TLS handshake delay | TLS and target protocol |
| Resource exhaustion | CPU, memory, thread pool |
| Insufficient timeout for legitimate workload | ALB and application timeout settings |

### Prevention

- Monitor application response latency.
- Optimize database queries and external API calls.
- Use CloudWatch alarms for `HTTPCode_ELB_504_Count`.
- Monitor `TargetResponseTime`.
- Ensure backend instances have sufficient resources.
- Configure realistic ALB timeout values.
- Use suitable client, application, and load balancer timeouts.
- Avoid unnecessary long-running synchronous requests.
- Consider asynchronous processing for lengthy operations.
- Use multiple backend targets across Availability Zones.
- Run performance and load tests before production deployments.

### Security Considerations

- Restrict backend port access to the ALB security group.
- Use HTTPS for production applications.
- Apply least-privilege IAM permissions.
- Protect application logs and credentials.
- Review infrastructure configuration through version control.
- Remove unused lab infrastructure.

## 20. Interview Questions and Answers

### Q1. What causes ALB HTTP 504 Gateway Timeout?

A common cause is a backend that does not respond before the ALB connection idle timeout expires.

### Q2. What caused HTTP 504 in this lab?

The backend application waited 20 seconds before responding, while the ALB idle timeout was 10 seconds.

### Q3. Can an ALB return HTTP 504 when its target is healthy?

Yes. The health endpoint may respond quickly while other application endpoints exceed the timeout.

### Q4. What is the default ALB idle timeout?

60 seconds.

### Q5. How do you modify the ALB idle timeout?

Using the `idle_timeout.timeout_seconds` load balancer attribute.

### Q6. What is the difference between ALB 502 and 504?

HTTP 502 commonly indicates an invalid backend response or a connection failure. HTTP 504 indicates a timeout while connecting to or waiting for the backend.

### Q7. Which CloudWatch metric tracks ALB-generated 504 errors?

`HTTPCode_ELB_504_Count`.

### Q8. How can you measure backend response time?

Use curl with the `time_total` output variable or application performance monitoring tools.

### Q9. Does increasing the ALB timeout always fix HTTP 504?

No. It may allow some legitimate long-running requests to finish, but it does not correct application performance problems or all network failures.

### Q10. What other issues can cause HTTP 504?

Backend connection timeouts, slow database queries, external API delays, network ACL problems, and backend TLS handshake delays.

### Q11. How can HTTP 504 be prevented?

Monitor response latency, optimize slow operations, configure suitable timeout values, and test application performance under load.

### Q12. How would you explain this lab in an interview?

I deployed an AWS Application Load Balancer with an EC2 backend running a Python HTTP application.

I configured the target group with health checks and set the ALB idle timeout to 10 seconds.

After establishing a healthy baseline, I introduced a 20-second delay in a test application endpoint.

The ALB began returning HTTP 504, although the EC2 instance and target group remained healthy.

I investigated the ALB timeout configuration, measured backend response time using curl, and reviewed CloudWatch metrics and application logs.

I identified the application response delay as the root cause, removed the fault, and verified that the ALB returned HTTP 200 again.

## 22. Lessons Learned

This lab demonstrates how an AWS Application Load Balancer can return HTTP 504 while the registered backend remains healthy.

Initially, the application responded successfully and passed ALB health checks.

We then introduced a 20-second delay on `/slow` while the ALB idle timeout was set to 10 seconds.

The backend remained available and eventually completed the request when accessed directly.

However, the ALB could not wait for the delayed response and generated HTTP 504.

The failure was caused by slow application processing relative to the configured timeout rather than an EC2 outage, unhealthy target, or security group problem.

Removing the delay restored successful HTTP responses.

**Key Lesson:** When troubleshooting ALB HTTP 504 errors, compare backend response times against the load balancer timeout settings. A healthy target does not guarantee every application endpoint responds quickly enough.
