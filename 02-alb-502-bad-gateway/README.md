# Lab 02 — ALB 502 Bad Gateway

## Overview

This lab demonstrates how to troubleshoot an **HTTP 502 Bad Gateway error generated by an AWS Application Load Balancer (ALB)**.

We deploy an internet-facing ALB with an Amazon EC2 backend running a custom Python HTTP application on port 8080.

The ALB forwards incoming requests from port 80 to the EC2 target group. The backend also provides a `/health` endpoint for ALB health checks.

Initially, both the health endpoint and main application return successful HTTP 200 responses.

We intentionally modify the application behavior so that normal requests return malformed HTTP data while the health check endpoint continues to respond with HTTP 200.

As a result, the ALB returns HTTP 502 Bad Gateway to clients even though the registered target remains healthy.

We investigate the ALB, target group, HTTP responses, backend application, and CloudWatch metrics before restoring normal application behavior.

**Troubleshooting workflow:**

Provision → Healthy Baseline → Fault Injection → Investigation → Root Cause Analysis → Remediation → Verification → Cleanup

## 2. Production Incident Scenario

### Incident Description

A company operates a web application behind an AWS Application Load Balancer.

The ALB receives HTTP requests from users and forwards them to a registered EC2 instance on port 8080.

The application exposes two endpoints:

- `/` — Main application endpoint.
- `/health` — Application health check endpoint.

The load balancer uses `/health` to monitor the registered target.

Following an application deployment, customers begin receiving HTTP 502 Bad Gateway errors.

However, the target group continues showing the EC2 target as healthy.

The cloud engineering team must investigate why health checks pass while application requests fail.

### Incident Symptoms

- ALB returns HTTP 502 for normal requests.
- Target group reports `healthy`.
- EC2 remains running.
- Backend application process remains active.
- TCP port 8080 is listening.
- `/health` returns HTTP 200.
- `/` returns malformed HTTP data.
- ALB listener and target group are configured correctly.
- Security groups permit ALB-to-EC2 connectivity.

### Business Impact

- Customers cannot access the application.
- Application availability decreases.
- User requests fail.
- Monitoring based only on target health may miss the problem.
- HTTP 502 errors increase.
- Application troubleshooting becomes necessary.

### Incident Objective

Identify why the ALB generates HTTP 502 errors despite a healthy registered target, correct the backend HTTP response, and restore successful application requests.

## 4. Understanding HTTP 502 Bad Gateway

An HTTP 502 Bad Gateway error occurs when a gateway or proxy cannot successfully process a response from an upstream server.

In AWS, an ALB can generate HTTP 502 when it encounters problems communicating with or interpreting responses from its backend targets.

### Common ALB 502 Causes

- Malformed HTTP response from a backend.
- Backend closes a connection unexpectedly.
- Backend resets a connection.
- Invalid or unsupported response headers.
- Incorrect backend TLS configuration.
- TLS handshake failure between ALB and target.
- Certain connection reuse or protocol compatibility problems.

### 502 vs. 503 vs. 504

| Error | Meaning | Common Cause |
|---|---|---|
| 502 Bad Gateway | Invalid backend response or connection failure | Malformed HTTP, reset connection |
| 503 Service Unavailable | No usable registered targets or unavailable service | Empty target group |
| 504 Gateway Timeout | ALB cannot complete request within time limits | Backend timeout |

### Important Concept

A healthy ALB target does not guarantee that every application endpoint works.

The ALB evaluates the configured health check endpoint, not every possible user request.

For this lab:

```text
GET /health → HTTP 200
GET /       → Invalid HTTP response
```

Therefore, ALB health checks may pass while normal requests fail with HTTP 502.

## 10. Create the Backend Application

Create `backend-user-data.sh`.

The Python application returns valid HTTP responses during normal operation and can simulate malformed HTTP responses when a fault file is present.

```bash
#!/bin/bash
set -eux

mkdir -p /opt/lab02

cat > /opt/lab02/app.py <<'PY'
#!/usr/bin/env python3

import socketserver
from pathlib import Path

FAULT_FILE = Path("/opt/lab02/enable-502")


class Handler(socketserver.BaseRequestHandler):
    def handle(self):
        self.request.settimeout(5)
        data = b""

        try:
            while b"\r\n\r\n" not in data and len(data) < 16384:
                chunk = self.request.recv(4096)

                if not chunk:
                    return

                data += chunk
        except (TimeoutError, OSError):
            return

        first_line = data.split(b"\r\n", 1)[0]
        path = first_line.split(b" ")[1:2]

        if path == [b"/health"]:
            body = b"OK\n"
            response = (
                b"HTTP/1.1 200 OK\r\n"
                b"Content-Type: text/plain\r\n"
                b"Content-Length: 3\r\n"
                b"Connection: close\r\n"
                b"\r\n" + body
            )

        elif FAULT_FILE.exists():
            response = b"NOT_AN_HTTP_RESPONSE\r\n\r\n"

        else:
            body = b"AWS ELB Lab 02 - Backend Healthy\n"
            response = (
                b"HTTP/1.1 200 OK\r\n"
                b"Content-Type: text/plain\r\n"
                + f"Content-Length: {len(body)}\r\n".encode()
                + b"Connection: close\r\n"
                + b"\r\n"
                + body
            )

        try:
            self.request.sendall(response)
        except OSError:
            pass


class Server(socketserver.ThreadingTCPServer):
    allow_reuse_address = True
    daemon_threads = True


with Server(("0.0.0.0", 8080), Handler) as server:
    server.serve_forever()
PY

cat > /etc/systemd/system/lab02-web.service <<'UNIT'
[Unit]
Description=Lab 02 ALB HTTP Response Test Server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/bin/python3 /opt/lab02/app.py
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
UNIT

systemctl daemon-reload
systemctl enable --now lab02-web.service
```

### Application Behavior

| Condition | `/health` | `/` |
|---|---|---|
| Normal | Valid HTTP 200 | Valid HTTP 200 |
| Fault enabled | Valid HTTP 200 | Malformed HTTP |
| Fault removed | Valid HTTP 200 | Valid HTTP 200 |

### Fault Control

Enable failure:

```bash
sudo touch /opt/lab02/enable-502
```

Disable failure:

```bash
sudo rm /opt/lab02/enable-502
```

The application detects the file during request handling, so restarting the process isn't required to enable or disable the simulated failure.

## 14. Reproduce ALB HTTP 502

### Step 1 — Connect to Backend

```bash

  --target "$INSTANCE_ID" \
```

## 16. Root Cause Analysis

### Root Cause

The backend application returned malformed HTTP data that the ALB could not interpret as a valid HTTP response.

### Technical Explanation

The ALB forwards an HTTP request to the backend on TCP port 8080.

A valid HTTP/1.1 response begins with a status line, followed by headers, a blank line, and the response body.

Example:

```http
HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 3

OK
```

During the incident, the backend instead returned:

```text
NOT_AN_HTTP_RESPONSE
```

Because this does not contain a valid HTTP response status line, the ALB cannot successfully process it.

The ALB generates HTTP 502 Bad Gateway.

### Why Did the Target Remain Healthy?

The target group checks `/health`.

That endpoint continued to return a valid HTTP 200 response.

The faulty behavior affected only the main application endpoint.

Consequently, the target passed health checks even while users experienced errors.

### Root Cause Flow

```text
Client Sends HTTP Request
            |
            v
ALB Forwards to EC2
            |
            v
Backend Receives Request
            |
            v
Malformed HTTP Response
            |
            X
ALB Cannot Parse Response
            |
            v
ALB Generates HTTP 502
            |
            v
Client Receives Bad Gateway
```

### Five Whys

1. **Why did the client receive HTTP 502?** The ALB could not process the backend response.
2. **Why couldn't the ALB process it?** The backend returned malformed HTTP data.
3. **Why did the backend return invalid data?** The fault injection changed the application's response behavior.
4. **Why was the target still healthy?** The health check endpoint continued responding correctly.
5. **How can this be prevented?** Validate backend responses, test application routes, monitor HTTP 502 errors, and use deployment checks.

## 18. Production Troubleshooting Best Practices

### ALB 502 Investigation Checklist

1. Verify ALB availability.
2. Inspect listener rules.
3. Confirm the correct target group.
4. Verify target registration.
5. Review target health.
6. Confirm target group protocol and port.
7. Verify security group rules.
8. Check backend application processes.
9. Confirm the backend port is listening.
10. Test HTTP responses directly from the backend.
11. Inspect backend logs for protocol errors.
12. Review ALB-generated 502 metrics.
13. Compare ALB-generated errors with target-generated 5xx errors.
14. Restore correct application behavior.
15. Verify HTTP 200 through the ALB.

### Common ALB 502 Causes

| Issue | Troubleshooting Focus |
|---|---|
| Malformed HTTP response | Backend HTTP status line and headers |
| Backend resets connection | Application logs and TCP behavior |
| Backend closes connection unexpectedly | Keep-alive and connection handling |
| Incorrect TLS configuration | Backend protocol and certificates |
| Backend protocol mismatch | Target group protocol and application listener |
| Invalid response headers | HTTP parser compatibility |
| Application crash during request | Process and application logs |

### Prevention

- Validate HTTP responses in CI/CD pipelines.
- Test critical application endpoints.
- Monitor `HTTPCode_ELB_502_Count`.
- Monitor application error rates.
- Keep health checks representative of application readiness.
- Implement structured application logging.
- Review application deployments.
- Use multiple backend targets across Availability Zones.
- Configure suitable connection and timeout settings.
- Use infrastructure as code for ALB resources.

### Production Security Considerations

- Restrict backend access to the ALB security group.
- Prefer HTTPS for public applications.
- Use valid TLS certificates.
- Avoid exposing backend management ports publicly.
- Apply least-privilege IAM permissions.
- Protect logs and monitoring data.
- Remove unused test infrastructure.

## 19. Interview Questions and Answers

### Q1. What does HTTP 502 Bad Gateway mean?

It means a gateway or proxy could not successfully process the response from an upstream server.

### Q2. What causes ALB-generated HTTP 502?

Common causes include malformed backend responses, connection resets, invalid headers, and TLS handshake failures.

### Q3. Can an ALB return 502 when targets are healthy?

Yes. The health endpoint can pass while other application endpoints return invalid responses.

### Q4. What is the difference between ALB 502 and 504?

HTTP 502 usually indicates an invalid backend response or connection problem, while HTTP 504 indicates a timeout.

### Q5. What is the difference between ALB 502 and 503?

HTTP 502 indicates a gateway/backend response problem. HTTP 503 generally indicates the load balancer cannot serve the request because suitable targets or resources are unavailable.

### Q6. Which CloudWatch metric tracks ALB-generated 502?

`HTTPCode_ELB_502_Count`.

### Q7. How do you distinguish ALB-generated and backend-generated HTTP errors?

Compare load balancer metrics, target metrics, backend logs, and ALB access logs if enabled.

### Q8. Why did the backend remain healthy in this lab?

The `/health` endpoint continued returning HTTP 200.

### Q9. Why didn't restarting the ALB solve the issue?

The problem originated in the backend HTTP response, not in the ALB infrastructure.

### Q10. What is a malformed HTTP response?

A response that does not follow the HTTP protocol's required format, such as an invalid status line or headers.

### Q11. What should you check first when users receive ALB 502?

Inspect the ALB error metric, target group, backend response, application logs, protocol configuration, and connection behavior.

### Q12. How would you explain this lab in an interview?

> I deployed an Application Load Balancer with an EC2 backend running a Python HTTP service. I configured a target group with health checks on `/health` and verified that the ALB returned HTTP 200.
>
> I intentionally configured the backend to return malformed HTTP responses for normal requests while keeping the health endpoint successful. The ALB began returning HTTP 502 even though the registered target remained healthy.
>
> I investigated the ALB listener, target group, backend application, HTTP response format, and CloudWatch metrics. I identified the invalid HTTP response as the root cause, removed the fault, and confirmed that the ALB returned HTTP 200 again.

## 22. Lessons Learned

This lab demonstrates how an Application Load Balancer can return HTTP 502 even when the registered backend target is healthy.

Initially, the application responded correctly to both health checks and normal requests.

After enabling the fault, the backend application continued running and listening on port 8080.

The health endpoint still returned HTTP 200, so the ALB continued reporting the target as healthy.

However, the main endpoint returned malformed HTTP data that the ALB could not process.

The resulting HTTP 502 error was caused by incorrect application behavior rather than an unavailable EC2 instance or a network security restriction.

Removing the fault restored valid HTTP responses and normal application functionality.

**Key Lesson:** A healthy ALB target does not guarantee every application route is functioning correctly. When troubleshooting HTTP 502, inspect the actual backend response format and application behavior rather than relying only on target health.
